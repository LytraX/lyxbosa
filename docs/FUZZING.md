# Fuzzing the hostile-input paths

Every byte this scanner reads was chosen by somebody who already owns the host. Two places
in the code parse those bytes rather than search them, and both are fuzzed:

| target | entry point | what it exercises |
| --- | --- | --- |
| `archive` | `ArchiveScanner::scan()` with the bytes in memory | libzip on a central directory, zlib on a deflate stream, this project's tar reader on header blocks, and the recursion between them |
| `content` | `MatchEngine::match()` | RE2 over the bytes, and the PHP constant folder that resolves identifiers a file assembles at run time |

The bodies of both live in `fuzz/FuzzTargets.h`. `fuzz/archive_fuzzer.cpp` and
`fuzz/content_fuzzer.cpp` are libFuzzer entry points around them, and
`tests/fuzz_replay_test.cpp` replays the seed corpus through the same functions in the
ordinary suite. One body, three callers: a replay that re-implemented the harness would
replay a crashing input through something that was never crashing.

## The fast half: every `ctest` run

The seed corpus is replayed by `lyxbosa_tests` in about a second, deterministically, with
no fuzzer and no container:

```
ctest --test-dir build -R FuzzReplay
```

It runs every file under `fuzz/seeds/` and `fuzz/regressions/` once, and it fails if the
corpus has shrunk, if most of the archive corpus stops being recognised as a container, or
if a known-good input stops producing the finding it used to.

**What it does not do.** That binary is built by the ordinary compiler with no sanitizers,
so it catches a crash, a hang and an assertion, and it does not catch an out-of-bounds read
that happens to land on a mapped page. Most of them do. For those, use the container.

## The slow half: a campaign

libFuzzer lives in clang's compiler-rt and has no GCC equivalent, so the fuzzers are built
where a clang exists, from a pinned base, with the build tree inside the container.

```
docker/fuzz/fuzz.sh build                  # first run also builds the image: a few minutes
docker/fuzz/fuzz.sh run archive 1800       # a bounded campaign, in seconds of wall clock
docker/fuzz/fuzz.sh run content 1800 -workers=12 -jobs=12
docker/fuzz/fuzz.sh replay                 # the corpus, once each, under the sanitizers
docker/fuzz/fuzz.sh reproduce archive fuzz/work/artifacts/archive/crash-<hash>
docker/fuzz/fuzz.sh minimise archive       # smallest set with the same coverage
docker/fuzz/fuzz.sh coverage archive       # line coverage this project's sources reached
```

Anything after the seconds argument is passed to libFuzzer unchanged.

Both binaries carry AddressSanitizer and UndefinedBehaviorSanitizer, and so do zlib,
libzip, re2 and abseil — `triplets/x64-linux-fuzz.cmake` says why instrumenting the
dependencies is not optional. UBSan runs with `-fno-sanitize-recover`, so an undefined
operation is a crash rather than a line on stderr that libFuzzer would never see.

## Where things are written

`fuzz/work/` — gitignored, and the only directory anything writes to. The repository is
mounted read-only inside the container, because a fuzzer copies its seeds, mutates them,
and writes a new file for every input it minimises; pointed at a tree somebody pushes, it
grows one nobody is watching.

The build tree is a docker volume, not a directory in the repository. `AGENTS.md` names
three build directories and says not to add a fourth; a sanitizer-and-fuzzer configure is
genuinely a different configuration rather than a workaround, and it is one that this
machine's compiler cannot produce at all. It lives where its compiler lives, exactly as
`docker/build/Linux/build-inside.sh` configures at `/build` inside its own container.

## Seeds

`fuzz/seeds/` is generated by `fuzz/make-seeds.py`, which reads nothing. Every seed is
synthetic and every one has a line of Python next to it saying which parser decision it is
aimed at, because libFuzzer finds a zip's magic in seconds and its central directory almost
never.

```
python3 fuzz/make-seeds.py            # write them
python3 fuzz/make-seeds.py --check    # fail if a committed seed was edited by hand
```

**A seed may never come from `trail-data/`, `corpus/local/` or `corpus/blobs/`.** The
reason is the multiplication above: held material used as a seed is copied and re-written
into hundreds of files in a directory that grows on its own. `corpus/shards/` is masked and
published and would be allowed; it is not used, because a shard row is a masked finding
rather than a container, and these targets want the shape of a parser's input.

## The guards are at their defaults

The harness reads a default-constructed `ArchiveConfig`, so it cannot drift from what ships:
depth, per-member size, total expansion, ratio and time budget are whatever `config/Rules.h`
says today. Turning a guard off is documented as the operator's decision and its
consequences are theirs — a hang found with `max_expansion` at zero is the documented
consequence of asking for it. A hang found with the guards on is a defect.

That decides the campaign's own timeout. `ArchiveConfig::timeBudgetSeconds` defaults to 60,
so an archive is *allowed* to work for a minute before its own guard stops it, and
`docker/fuzz/build-inside.sh` passes `-timeout=90` rather than something snappier: below the
budget, libFuzzer would report the guard doing its job as a hang.

## Triaging a finding

A crash writes its input to `fuzz/work/artifacts/<target>/`. Shrink it, confirm it, then
decide where it belongs:

```
docker/fuzz/fuzz.sh reproduce archive fuzz/work/artifacts/archive/crash-<hash>
```

An input that reproduces and is this project's own code becomes a case in the ordinary
suite and its bytes go in `fuzz/regressions/<target>/`, which the replay picks up
automatically and which `make-seeds.py` never rewrites. An input that reproduces inside a
dependency is a different problem with a different owner, and the reproducer belongs
upstream.
