# Fuzzing the hostile-input paths — spike, 2026-09-12

**Question.** Nobody had ever fed this scanner hostile bytes on purpose. It opens zip, tar,
tar.gz and gz through libzip and zlib, walks hostile PHP through a constant folder that
resolves assembled identifiers, and runs RE2 over whatever it finds. An outside security
review read the source and reproduced five operational defects, and was explicit that it
fuzzed nothing and established nothing about resistance to parser crashes or resource
exhaustion. The single adversarial-input problem anybody had found was found by hand, which
is a statement about how hard people had looked rather than about what is there.

**Answer. Both gates pass, and the second one passes empty.** A libFuzzer harness builds
against `ArchiveScanner::scan()` and `MatchEngine::match()` under AddressSanitizer and
UndefinedBehaviorSanitizer, reaches **80.7% of the lines** of the archive readers and
**73.0%** of the constant folder, and found **nothing** in 30 minutes on 24 concurrent
workers — no crash, no sanitizer report, no allocation failure, no hang. The rig was
watched reporting a planted defect before that result was believed.

## Gate one: a harness that builds and reaches the code

**The seam is the public entry point, not the private ones.** `scanZip` takes a `ZipReader`
rather than a `ByteSource`, so the three private methods are not one seam. The public
`ArchiveScanner::scan(path, kind, inMemory)` is: it takes the bytes directly, reads the path
only when the buffer is empty, and covers all four formats through the same
`ZipReader::openBuffer` / `MemorySource` split that a real scan uses for a file it has
already read.

**The format is sniffed, not selected.** `archive::sniff()` decides what the input is,
exactly as `Scanner` does, rather than a selector byte at the front of the input. That costs
reach and buys the property that matters: every crash this can find is one that can be
reached by putting a file on a host and running a scan.

**Toolchain.** clang 18 in `docker/fuzz/`, from `ubuntu:24.04`, with the vcpkg dependency
graph built in a cached image layer — eighteen ports in 141 s. Both fuzz binaries carry
ASan and UBSan with `-fno-sanitize-recover`, and so do zlib, libzip, re2 and abseil:
`triplets/x64-linux-fuzz.cmake` instruments those four and not the rest, because ASan only
reports an out-of-bounds access when the code performing it was instrumented, and because
libFuzzer steers by coverage it cannot see inside an uninstrumented parser.

**No fourth build directory.** The configure lives at `/builds/fuzz` inside the container
and the tree is a docker volume, the same shape as `docker/build/Linux/build-inside.sh`.
`AGENTS.md` gained the general rule rather than an exception: a configuration this machine's
compiler cannot produce lives where its compiler lives.

One thing fought, and it named the wrong culprit. CMake 3.28 with Ninja and C++20 runs a
module dependency scan that needs `clang-scan-deps`, which Ubuntu ships in `clang-tools`
rather than in `clang`; without it the configure fails inside `FindThreads` with
`Could NOT find Threads`. Nothing here is a C++20 module, so the scan is off.

### The rig was observed reporting a defect

A check that has never been seen to fail is not yet a check, and that applies to the fuzzer
before it applies to anything the fuzzer says. On a **copy of the tree in a scratch
directory** — never the tree itself — a one-byte heap over-read was planted in
`ZipReader::loadIndex`, reachable from any zip with one named entry:

| step | result |
|---|---|
| `fuzz.sh replay archive` on the planted tree | `heap-buffer-overflow`, symbolised stack naming `loadIndex` → `openBuffer` → `ArchiveScanner::scan` → `runArchiveTarget` → `LLVMFuzzerTestOneInput` |
| artifact written | `crash-7d7b0550…`, 124 bytes, on the host |
| `fuzz.sh reproduce archive <artifact>` | reproduces, naming the input |
| the ordinary gcc `ctest` replay on the same planted tree | **5 of 5 cases pass** |

That last row is the honest measure of the fast regression: it catches a crash, a hang and
an assertion, and it does not catch an over-read that lands on a mapped page. The sanitizer
build is what catches that class, and it is the reason the container exists.

## Gate two: what a bounded run found

**Budget: 30 minutes of wall clock per target, both targets at once, 12 libFuzzer workers
each** — 24 concurrent fuzzers, about 12 CPU-hours. Started 08:47:14Z, ended 09:17:16Z.

| | archive | content |
|---|---|---|
| executions | 19,692,075 | 3,289,454 |
| coverage edges, seeds → campaign | 5,211 → 7,067 | 3,979 → 5,515 |
| corpus, seeds → grown → minimised | 24 → 68,815 → 2,900 | 14 → 42,440 → 3,776 |
| crashes, sanitizer reports, OOM, hangs | 0 | 0 |
| slowest single input | under 1 s | under 1 s |
| peak resident set per worker | 585 MB | 585 MB |

The guards were at their shipped defaults throughout, read from a default-constructed
`ArchiveConfig` so the harness cannot drift from what ships. Nothing came near them: with
`timeBudgetSeconds` at 60 and `maxExpansion` at 256 MB, no input in 23 million executions
took a measurable second or held more than 585 MB, against limits of 90 s and 4 GB.

### Coverage, by the area each target aims at

| area | lines | regions | branches |
|---|---|---|---|
| `src-lib/cpp/archive/` (archive target) | **80.68%** | 84.58% | 77.64% |
| `analysis/StringAssembly.cpp` (content target) | **72.96%** | 69.94% | 66.82% |
| `rules/obfuscation.cpp` (content target) | 73.40% | 79.12% | 74.69% |
| `core/LiteralPrefilter.h` (content target) | 91.95% | 88.73% | 77.42% |

Per file in the archive readers: `ArchiveIndex.cpp` 99.37%, `TarReader.cpp` 92.45%,
`GzipSource.h` 87.69%, `ArchiveScanner.cpp` 83.38%, `ZipReader.cpp` 77.32%,
`ArchiveFormat.cpp` 51.16%, `ByteSource.h` 54.72%.

**Two denominators are deliberately not quoted.** The whole-tree figures the tool also
prints — 47.15% and 31.79% of lines — include `Scanner.cpp`, `FileWalker.cpp` and
`Quarantine.cpp`, which sit at 0% because neither target walks a tree or moves a file. A
denominator that includes code the measurement never aimed at bounds the tool, not the
result. And the coverage above was measured over the corpus **the fuzzer itself grew**, so
it says what this harness reached and not what is reachable.

The two files at the bottom of the archive list say the same thing in reverse, and they
are the harness's own limit rather than dead code: `ArchiveFormat.cpp` holds `sniffFile()`
and `ByteSource.h` holds `FileSource`, both of which read from a path. A harness that feeds
bytes in memory never enters them. `ArchiveScanner::countMembers()` is unreached for the
same reason — it takes a path and calls `ZipReader::openFile`. Its body is thin and
everything it calls afterwards (`loadIndex`, `selectionSkip`, the entry loop) is covered
through `openBuffer`, so what is genuinely unfuzzed is libzip's file-backed source rather
than any of this project's logic.

## Findings

**None in the product.** No crash, no sanitizer report, no allocation failure, no hang, in
23 million executions at the coverage above.

That is a bound and not a proof, and the size of the bound is the coverage figure rather
than the execution count. What can be said: the parts of the archive readers this harness
reaches — 80.7% of their lines, including 99% of the index classifier and 92% of the tar
reader — survive 30 minutes of directed mutation with the sanitizers on, and the rig that
says so was watched reporting a planted defect in that same code minutes earlier.

**One finding in the harness, fixed.** The first version of the seed `tar-bad-size.tar`
spliced a huge size into a tar header without recomputing the checksum. `TarReader`
verifies the checksum before it reads the size, so the seed was turned away at the door and
never reached the arithmetic it existed to exercise — a seed that cannot enter the code it
was written for, which is the same shape of failure as a check that cannot fail. Measured
both ways with `lyxbosa check`:

| seed | what the scanner reports |
|---|---|
| spliced header, checksum not recomputed | `Members not scanned: 1 (1 corrupt)` |
| `tar-huge-size.tar`, checksum over an 8 GB claim | `Members not scanned: 2 (1 over size limit, 1 corrupt)` |

The second reaches the member-size guard. The first never got past the header check.

## What was left behind that runs

`ctest --test-dir build -R FuzzReplay` — five cases, **1.2 s**, no fuzzer and no container,
replaying every file under `fuzz/seeds/` and `fuzz/regressions/` through the same functions
the fuzzer calls. It is in `lyxbosa_tests`, so it already runs in CI wherever `ctest` does.

Its three controls have been watched failing, each against a doctored copy in a scratch
directory rather than against the tree:

| control | doctored corpus | result |
|---|---|---|
| the harness reaches the scanner | `zip-webshell.zip` replaced with a benign member | `FAILED` — "the rule engine never ran over the member's bytes" |
| the corpus has not shrunk | empty seed directories | `FAILED` — both cases refuse rather than passing on nothing |
| the corpus still enters the parsers | 25 files `sniff()` turns away | `FAILED` — "only 0 of 25 archive inputs were recognised as containers" |

`corpus/control-suites.py` is deliberately **not** extended to discover it. That runner
answers whether the corpus tools' `--inject` controls still work, and its discovery reads
`corpus/*.py` and `corpus/*.sh`. This regression is a C++ test whose runner is `ctest`,
which already runs on every build of this tree; putting it behind a second runner would
give it two owners and no clear one. `fuzz/make-seeds.py --check` is a convenience for
whoever regenerates the seeds, not a gate — the property that matters, that the seeds still
enter the parsers, is asserted by the replay itself.

`docs/FUZZING.md` is the procedure for a longer campaign by hand.
